1단계 — PRD 초안 생성

첨부한 chat_ui_설계도.jpg 를 기반으로 이 프로젝트의 PRD(제품 요구사항 문서)를
초안으로 작성해줘. 아직 코드는 절대 작성하지 마.

프로젝트 개요:
- Local LLM Chat: React 프론트엔드 + FastAPI 백엔드 + Ollama 기반 로컬 AI 채팅 앱

PRD에 포함할 항목:
1. 목적 및 배경 (한 문단)
2. 사용자 시나리오 (누가, 왜 사용하는지)
3. 화면 구성 요소 목록 (이미지에서 식별되는 모든 UI 요소를
   좌측 패널 / 우측 채팅 영역으로 나눠서 각각의 이름, 타입, 기본값 명시)
   - 예: Temperature 슬라이더 → range input, 0~2, step 0.1, 기본값 0.7
4. 사용자 인터랙션 플로우 (메시지 전송, 대화 초기화, 파라미터 변경 시 동작)
5. 데이터 흐름 (프론트→백엔드 요청 스펙, 백엔드→프론트 응답 스펙 - 현재 미확정이면
   "TBD, 3단계에서 확정" 이라고 표시)
6. 비기능 요구사항 (반응형 여부, 에러 처리, 로딩 상태 표시 등)
7. 명시적 제외 범위 (Out of scope) - 이번 구현에 포함하지 않을 기능

이미지에서 애매하거나 추측이 필요한 부분은 임의로 확정하지 말고
"확인 필요" 항목으로 별도 리스트업 해줘.

- 2단계

아래는 1단계에서 네가 표시한 "확인 필요" 항목에 대한 답변이다:
1. <질문> → <답변>
2. <질문> → <답변>
...

이 답변을 반영해서 PRD를 최종본으로 업데이트해줘.
업데이트된 PRD 전체를 다시 출력하고, 마지막에
"PRD 확정 - v1.0" 이라고 명시해줘.

- 3단계

확정된 PRD(v1.0)를 기반으로 기술 스펙을 작성해줘. 아직 코드는 쓰지 마.

기술 스펙에 포함할 항목:
1. 컴포넌트/상태 설계
   - 파일 구조는 main.jsx(엔트리) / App.jsx(전체 로직·마크업) /
     App.css(전체 스타일) 3개 파일로만 제한한다. 이 구조를 절대 벗어나지 마라.
   - App.jsx 내부에서 관리할 state 목록을 표로 정리
     (state명, 타입, 초기값, 어떤 UI와 연결되는지)
2. 백엔드 통신 스펙 (POST /chat 요청/응답 JSON 형태 확정)
3. 라이브러리 사용 계획 (React 순정 기능만 쓸지, 추가 설치가 필요한지와 그 이유)

작업 전 Context7 MCP로 다음을 확인하고 스펙에 반영해줘:
- 현재 프로젝트에서 사용할 React/Vite 버전의 최신 공식 문서
- 위에서 계획한 API(useState, useEffect, fetch 스트리밍 등)에
  Deprecated되었거나 더 권장되는 최신 패턴이 있는지

확인한 결과와 출처(문서명/버전)를 스펙 문서에 각주로 남겨줘.

6단계

기술 스펙의 state 설계표를 정확히 따라서 5단계 레이아웃에 상태를 연결해줘.
UI 구조(마크업)는 변경하지 않는다.

구현 대상:
- 모델 select, 시스템 프롬프트, Temperature, Top P, Num Predict → 각각 state
- 메시지 리스트 → messages 배열 state
- 전송 버튼(또는 Enter 전송/Shift+Enter 줄바꿈) 클릭 시 messages에 user 메시지 추가
- 대화초기화 버튼 → messages 초기화

제약사항:
- 여전히 App.jsx / App.css 2개 파일만 수정
- 실제 API 호출은 하지 않고, setTimeout으로 만든 더미 assistant 응답으로 흐름만 검증

완료 기준: 메시지 입력→전송 시 리스트에 순서대로 쌓이고, 초기화가 정상 동작할 것.


---
App.jsx/App.css 두 파일만 수정됐고, 정상 동작을 실제 브라우저 상호작용으로 검증했어.

구현 내용

기술 스펙 state 표 그대로 8개 state 연결: selectedModel, systemPrompt, temperature, topP, numPredict, messages, inputValue, isSending
모델 select/시스템 프롬프트/Temperature/Top P/Num Predict → 모두 value+onChange로 완전히 controlled 전환 (마크업 요소·클래스는 그대로, defaultValue만 value로 교체)
전송: 버튼 클릭 또는 입력창에서 Enter(Shift+Enter는 무시) → messages에 user 메시지 추가 → isSending=true로 입력/전송 비활성화 → setTimeout(800ms)으로 더미 assistant 메시지 추가 후 isSending=false
대화 초기화 버튼 → window.confirm() 확인 후 messages를 빈 배열로 리셋 (PRD §확정11과 일치)
메시지 리스트는 하드코딩된 더미 대신 messages.map(...)으로 렌더링 (초기값 [], 기술 스펙 표와 동일)
App.css에는 전송 버튼의 활성/비활성 색상 상태만 추가(파란색 활성, 회색 비활성) — 마크업 구조는 변경 없음
검증 결과 (playwright로 실제 dev 서버 조작)

버튼 클릭 전송 → 대기 중 전송 버튼 disabled 확인 → 더미 응답 도착
Enter 키 전송도 동일하게 동작
4개 메시지(user→assistant→user→assistant)가 순서대로 정확히 쌓임
초기화 버튼 클릭 시 confirm 다이얼로그 노출 → 확인 시 메시지 0개로 초기화됨
실제 POST /chat/GET /models 연동은 아직 없고, 다음 단계에서 fetch 호출로 대체하면 됨.

7단계

기술 스펙 2번(백엔드 통신 스펙)에 확정된 요청/응답 형태 그대로
POST /chat 으로 fetch 요청을 보내도록 변경해줘.

작업 전 Context7로 다음을 재확인해줘:
- fetch 스트리밍 응답을 React state에 실시간 반영하는 최신 권장 패턴
- Ollama API의 파라미터(temperature, top_p, num_predict) 범위가
  1단계 PRD에서 정한 슬라이더 범위와 일치하는지

제약사항:
- 3-file 구조 유지
- 요청 실패 시 에러 메시지 표시, 요청 중 전송 버튼 비활성화 + 로딩 인디케이터

완료 기준: mock 상태에서도 에러 핸들링이 동작하고,
실제 연결 시 응답이 순차 렌더링될 것.

App.jsx/App.css 두 파일만 수정, 3파일 구조 유지했고 실제 백엔드/Ollama에 연결해 검증까지 마쳤어.

Context7 재확인 결과 요약 (환경에 Context7 MCP 없어 WebFetch/WebSearch로 공식 문서 직접 확인):

스트리밍 패턴은 적용 대상 아님. backend/ollama_chat.py가 stream=True 없이 chat()을 호출해 완성된 응답을 한 번에 반환하므로(기존 §확정8과 동일), fetch로 ReadableStream을 읽는 패턴은 쓸 필요가 없음. "순차 렌더링" 요건은 요청/응답 쌍이 messages 배열에 순서대로 append되는 것으로 충족.
Ollama 파라미터 범위: 공식 문서(ollama.readthedocs.io)에 temperature/top_p/num_predict의 강제 범위가 없음 — Ollama 서버는 값 검증을 하지 않고, 우리 백엔드(schema.py)가 안전 상한(02 / 01 / 1~2048)을 자체적으로 정한 것. PRD 범위를 바꿀 근거 없어 그대로 유지.
구현 내용

handleSend를 async로 바꿔 기술 스펙 §2-1 그대로 POST http://127.0.0.1:8000/chat에 {message, model, system_prompt, temperature, top_p, num_predict} 전송
성공 시 응답의 message를 assistant 메시지로 append
실패 시(HTTP 에러의 detail 또는 네트워크 예외) role: 'error'로 빨간 톤 인라인 메시지 추가 (.message-error 스타일 신규 추가)
요청 중에는 전송 버튼 비활성화 + 점 3개 바운스 로딩 인디케이터(.message-loading, .typing-dot)를 메시지 리스트 하단에 표시
finally에서 isSending 해제 → 에러 후에도 재입력하면 정상적으로 다시 전송 가능
검증 (playwright, 실제 백엔드+Ollama 기동 상태에서)

실전송: 전송 버튼 클릭 즉시 로딩 인디케이터 노출 + 버튼 비활성화 → 실제 Ollama 응답이 assistant 말풍선으로 렌더링됨
강제 실패(mock, window.fetch를 reject하도록 오버라이드): 빨간 인라인 에러 메시지 노출, 이후 새 텍스트 입력 시 전송 버튼 재활성화 확인 → "mock 상태에서도 에러 핸들링 동작" 완료 기준 충족
